# AGENTS.md — MCEndgame

Guidance for AI agents and contributors working on this repository. Read this before
modifying code. It explains how the mod is wired together and the conventions you must
follow so your changes fit in.

## What this project is

**MCEndgame** is a Minecraft **Fabric mod** (mod id `mcendgame`) that adds ARPG-style
endgame content: procedurally generated dungeons, boss fights, a custom attribute /
itemization system, totems, crystals (item crafting/corruption), and "aspects" that
modify a dungeon before you enter it. It is written mostly in **Kotlin** (with Java for
mixins and low-level runtime-world code) and published on Modrinth / CurseForge.

### Tech stack (see `gradle.properties` for exact versions)

- Minecraft **26.2** (calendar versioning), **Yarn** mappings, Fabric Loom
- **Kotlin 2.4.0** via Fabric Language Kotlin, **Java 25** toolchain
- Fabric API, **GeckoLib** (entity/armor animations)
- **maucon-framework** (`de.maucon:maucon-framework:2.0.1`) — a private dependency from
  GitHub Packages (`maven.pkg.github.com/maucon/maucon-framework`) that provides the
  dependency injection, event bus, command bus, and initializer machinery the whole mod
  is built on. It is bundled (`include`) into the release jar.

### Building requires credentials

The maucon-framework maven is private. Any Gradle invocation needs:

```powershell
$env:GITHUB_PACKAGES_NAME = "<github-username>"
$env:GITHUB_PACKAGES_TOKEN = "<github token with read:packages>"
```

Without these, dependency resolution fails. CI passes `github.actor` /
`secrets.GITHUB_TOKEN` automatically.

## How the mod is wired (critical)

The mod has **almost no explicit initialization code**. Both entry points just do:

```kotlin
MauConFramework.start(MCEndgame::class.java)      // or MCEndgameClient::class.java
```

`MauConFramework.start()` scans the entry-point's package and subpackages for classes
annotated `@Injectable`, instantiates them with constructor dependency injection, runs
`@Initializer` methods, then registers `@EventSubscriber` and `@CommandHandler` methods.
**Consequence: nearly everything in `component/` and `messaging/` is an `@Injectable`
object/class and is discovered automatically. You rarely register anything manually —
you just add annotated code in the right package and it gets wired.**

Framework API (from maucon-framework; inspect
`~/.gradle/caches/modules-2/files-2.1/de.maucon/maucon-framework/2.0.1/...-sources.jar`):

- `@Injectable` — marks a class (or a provider method inside `@Configuration`) as a
  component. Constructor params are injected by type; `@Qualifier("name")` selects a
  named component; `@Logging` injects an slf4j `Logger`.
- `@Configuration` — class holding `@Injectable` factory methods (see `FabricConfig`,
  `RuntimeConfig`).
- `@Initializer(priority)` — method run once after injection; used heavily to register
  Fabric event listeners (see `EventMapper`).
- `EventGateway.publish(event)` / `@EventSubscriber(sync = true|false)` — mod-internal
  events. `sync = true` runs on the caller thread; default runs async on a coroutine.
  Subscribers are matched by the single method parameter type (supertypes match too).
- `CommandGateway.apply(command)` / `@CommandHandler(priority, ignoreCancelled)` —
  mod-internal commands (used for cross-cutting queries/mutations like damage
  collection). Handlers run in priority order; the (possibly mutated) command is
  returned.

### Messaging pattern (events + commands)

`main/messaging/` defines the mod's own message types, grouped by feature
(`dungeon/`, `misc/`, `server/`, `crystals/`, `collect_attribute/`, `totem_encounter/`, ...):

- **Events** (suffix `Event`) — "something happened" notifications, e.g.
  `LivingEntityDeathEvent`, `DungeonGeneratedEvent`, `PlayerJoinEvent`.
- **Commands** (suffix `Command`) — request/response-ish messages, e.g.
  `CollectCustomAttributesCommand`, `DungeonGenerateCommand`, `DamageItemStackCommand`.

`EventMapper.kt` is the bridge from Fabric's lifecycle events to these mod events
(e.g. it registers `ServerLifecycleEvents.SERVER_STARTING` in an `@Initializer` and
publishes `ServerStartingEvent`). Add new event bridging there.

### Runtime configuration

`RuntimeConfig` (a `@Configuration` object) populates these singletons on
`ServerStartingEvent` — use them instead of storing your own references:

- `SERVER: MinecraftServer`
- `RUNTIME_WORLDS: RuntimeWorlds` — creates/ticks/deletes temporary dungeon dimensions
- `WORLD_SAVE_PATH: Path` — the world save root
- `REGISTRY_OPS: RegistryOps<JsonElement>` — needed for codec encode/decode

`FabricConfig` provides `FabricLoader`.

### Feature modules under `component/`

Everything lives in `component/<feature>/` and is auto-discovered. Major ones:

- `dungeon/` — generation (layout generators, room types, encounters), enemies + bosses,
  level/seed, loot, world lifecycle (`DungeonWorldService`), types
- `custom_attribute/` — the itemization core: `Attribute`, `AttributeType`,
  `CustomAttributeTypes` / `VanillaAttributeTypes`, `data/` (rolls, bounds),
  `effects/` (one `*Service` per attribute effect), `affinity/`, `sign_based_keyword/`
- `item/` — `custom/` items: armor sets (`armor/item/<name>/`), `aspect/`, `crystal/`,
  `totem/`, `tool/`, `misc/`; registration via `UniqueItemRegistry` /
  `RegistryUtil`; `equipment/` helpers
- `entity/` — `types/` + `custom/` custom entities (`entities/<name>/`), attacks
  (`attack/`), goals, interfaces (e.g. `MeleeAttackMob`, `TeleportAttackMob`),
  networking, sound
- `block/` — `blocks/dungeon_device/`, `crystalforge/`, `totem_statue/`
- `totem/`, `corruption/`, `damage/`, `stats/`, `killer/`, `item_filter/`, `portal/`,
  `screen/`, `status_effect/`, `world/`, `biome/`, `dimension/`, `analytics/`,
  `config/`, `chat_commands/`, `tags/`, `particle/`, `sound/`, `inventory/`

### Persistence

`functional/persistent_repository/PersistentMapRepository` is the base class for
JSON-file-backed repositories (each feature has a `db/` subpackage, e.g.
`dungeon/world/db/DungeonWorldRepository`). Entities implement the framework's
`Entity<ID>` interface and use a Mojang `Codec`; data is saved to
`<world>/mcendgame/repository/<name>.json` on server stop / player disconnect and
loaded on server start. Follow this pattern for new persisted state.

## Build, run, and test

```powershell
# always needs GITHUB_PACKAGES_NAME + GITHUB_PACKAGES_TOKEN (see above)

.\gradlew runDatagen          # regenerate src/main/generated (tags, loot, models, recipes, damage types, worldgen, registries)
.\gradlew build               # compile + datagen-dependent build; jars in build/libs/
.\gradlew runClient           # launch the client with the mod (dev environment in run/)
.\gradlew runServer           # dedicated server
.\gradlew runGameTest         # server gametests
.\gradlew runClientGameTest   # client gametests
.\gradlew runProductionClientGameTest  # production-style client gametest (used in CI, uses xvfb)
.\gradlew test                # JUnit tests (fabric-loader-junit)
```

CI (`.github/workflows/build.yml`) runs `runDatagen` then `build` (or
`runProductionClientGameTest`), so datagen output must be committed-consistent: after
changing anything that feeds datagen (blocks, items, tags, recipes, loot, models),
re-run `runDatagen` and check in the regenerated `src/main/generated` files. Note
`src/main/generated` is gitignored in this checkout — regenerate locally when needed.

## Coding conventions

- **Formatting**: IntelliJ-style `.editorconfig` at repo root — 4-space indent, CRLF
  line endings, 190 max line length, continuation indent 8. Match surrounding style.
- **Language split**: new gameplay logic in **Kotlin**. Java is used only for mixins
  and the runtime-worlds plumbing — keep new code in Kotlin unless there's a reason.
- **Naming**: message types end in `Event` / `Command`; attribute effect services end
  in `Service`; util helpers are top-level extension functions in `util/extension/`
  (files named `XxxExtension.kt`); mixin accessor bridges live in
  `util/extension/mixin/`.
- **Mixins & access wideners**: never reference private Minecraft members directly.
  Add a mixin in `main/mixin/<concern>/` (or `client/mixin/...` for client), register
  it in the corresponding `mcendgame.mixins.json` / `mcendgame.client.mixins.json`,
  and expose accessors as `XxxAccessor` interfaces. If a member needs widening (e.g.
  `ServerClockManager` internals), add it to `src/main/resources/mcendgame.accesswidener`.
- **Registries**: register items/blocks/entities via `util/minecraft/RegistryUtil`
  (wraps vanilla registry registration); unique items additionally go through
  `UniqueItemRegistry` so `/giveunique` and related systems can find them.
- **Data components**: custom item data (e.g. `custom_attributes`) is stored via
  custom `DataComponentType`s registered through `RegistryUtil.registerDataComponentType`.
- **Events**: prefer `sync = true` for gameplay-critical handlers (ordering matters);
  use async only for genuinely fire-and-forget work. Keep event/command classes small
  data holders.
- **Client/server split**: anything touching rendering/screens/keybinds goes in
  `src/client`; the client source set can see `main` but not vice versa
  (`splitEnvironmentSourceSets`). Mirror common constants in both sides or share via
  payload/network code in `main`.

## Common tasks

- **Add a custom item** (e.g. a new unique): create the item class in
  `component/item/custom/<category>/`, register it via `UniqueItemRegistry` +
  `RegistryUtil`, add datagen entries (model provider, tags, loot if it drops) and a
  lang key in `assets/mcendgame/lang/`, then run `runDatagen`.
- **Add a new attribute effect**: add the attribute to `CustomAttributeTypes` (or
  `VanillaAttributeTypes`), create an effect service in
  `component/custom_attribute/effects/`, and hook it into the relevant event/command
  pipeline (damage events, tick events).
- **Add a new dungeon enemy/boss**: model it after `component/entity/custom/entities/<name>/`
  (entity class + `CustomEntities` registration + GeckoLib model/animation assets +
  textures + entity attributes) and wire its spawn into `dungeon/enemy/` generation.
- **Add a new mod event**: create the event class in `messaging/<feature>/`, publish it
  with `EventGateway.publish(...)`, and subscribe with `@EventSubscriber` in an
  `@Injectable` component. If it originates from Fabric, bridge it in `EventMapper.kt`.

## Gotchas

- **Every Gradle command needs the GitHub Packages credentials** — a build that fails
  with "Could not GET ... maven.pkg.github.com" is almost always missing
  `GITHUB_PACKAGES_NAME` / `GITHUB_PACKAGES_TOKEN`.
- Minecraft 26.2 uses the new **calendar versioning** and **Yarn mappings**; class names
  here are Yarn (e.g. `ServerLevel`, `Level`, `Identifier`) — do not mix in Mojang-mapped
  names from older knowledge.
- `@Injectable` components are instantiated eagerly at startup — avoid heavy work in
  constructors; use `@Initializer` for setup that needs the server/runtime.
- The mod collects **analytics** by default; dev/test runs disable it by writing
  `config/mcendgame.json` (`{"sendAnalytics": false}`) — build.gradle does this for the
  test tasks automatically. Keep that behavior when adding new test tasks.
- `run/`, `logs/`, `.gradle/`, `build/`, `src/main/generated/`, `.kotlin/`, `.idea/`
  are gitignored — never commit dev artifacts.
